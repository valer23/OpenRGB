## Fans: packet correctness invalid because of evaluator input defect; diagnostic correction required; build pending; hardware pending

### [P2] Re-arm failure reporting after a fully recovered lighting update

Location: fans/Controllers/LianLiController/LianLiUniHubSLInfinityController/LianLiUniHubSLInfinityController.cpp:351-362, with commit completion at lines 140-147 and 234-241.

CheckReportResult permanently sets report_error_logged on the first error and never clears it. For example, an initial setup/colour failure can be followed by fully successful frames and then a persistent commit failure; all new commit failures are silent, and the bool returned by SendCommitAction is discarded by both update paths. Only the unrelated first error is observable. Preserve suppression during consecutive failing/partially recovered frames, but clear the latch after a complete successful colour-and-commit update so a new failure episode produces one diagnostic. Clearing it after every successful individual report would instead flood logs when colour succeeds and commit repeatedly fails. Add an exercised fail/succeed/fail-commit sequence when evaluator runtime tests become available.

Other inspected changes fit the existing abstraction: no new controller framework; exact seven-byte feature setup/commit and 353-byte colour output; native Windows waits; RBG and existing brightness/effect colour construction retained; colour failure gates commit. Physical port counts use the larger paired zone with ceiling division, cache only successful changed counts, and sparse/empty channels do not return out of the whole loop. Cooling commands and detector identity are unchanged. Windows header version encoding makes the 0x00000F00 guard select the bundled 0.15 control-output API. Older-header fallback is disclosed as unverified.

Evaluator input defect, not an agent protocol failure: the original evidence-fans.md incorrectly instructed a packed direction/speed byte and brightness at byte 4. Line 334 follows that premise and explicitly labels the chosen nibble interpretation. INPUT-CORRECTIONS.md records the correct separate-field layout as E0, 10+channel, effect, speed, direction, brightness, 00, with zero static defaults after effect 01. Thus this frozen packet cannot be accepted as correct, but must not count as a fair worker failure or as evidence for guidance quality. The diagnostic-recovery finding above is independent of this malformed input.

Remaining evidence gates: compile the real platform branches/link symbols; execute report-count/type/length/fault tests including paired-count changes, later sparse channels, partial groups, failed commits and recovery; physical static/effect/streaming checks on the 3/2/1/0 layout. Prior physical observations are supplied inputs, not tests of this revision.

## ASUS: initial review pass; build pending; hardware pending

I checked the narrow IPU detector, no writes from constructors/detection, zero-filled 64-byte reports, initialization selector order 00/01, byte 8, activation byte 3, 2200/1000 ms waits, 30 ms report spacing, both same-colour outputs, and GRB offsets 18/19/20 against the supplied capture. This supports the architectural choice but does not prove linking. Restricting this device registration to Windows is consistent with supplied API availability and evidence limits.

Remaining evidence gates: actual Windows compilation/linking against the configured dependencies; executed negative/short transfer tests at every initialization and colour step, subsequent recovery and warning suppression; real enumeration, initial no-write behavior, colours and service exclusion on the board. Linux/macOS were not claimed. One combined logo zone follows the limited physical mapping evidence; two independently named physical outputs would not be justified.

## RAM: initial review pass; build pending; hardware pending

No definite source-level blocker found in ram/i2c_smbus/Windows/i2c_smbus_pawnio.cpp. I compared its frozen complete file/patch with baseline Git HEAD and traced the normal transaction access convention. At lines 52-83, port selection opens the same GLOBAL_SMBUS_MUTEX_NAME used by normal transfers and executes only after WAIT_OBJECT_0 or WAIT_ABANDONED. Both acquired outcomes reach ReleaseMutex and CloseHandle; create/wait failures skip execution, close any opened mutex and never release unowned ownership. Release failure is logged and rejects registration. This correctly handles the abandoned-ownership distinction.

At lines 423-463, each successful PawnIO start registers only after successful selection and sets bus_detected on that path; failed selection closes the rejected PawnIO handle. Successful names, port indices and ownership through the existing bus destructor are preserved. The patch changes neither RAM/UI deduplication nor other backend detection. Temporary selection-mutex ownership is separate from the later bus-owned runtime mutex handle; the shared name still provides cross-process serialization during selection.

The helper preserves the baseline HRESULT contract. The unused output word and returned length have no supplied module semantic, so inventing an output-length success condition is not justified from these inputs. This is an evidence limitation, not proof of a missing required payload check. The report accurately discloses binary-module internals and no physical validation. I ran tracked git diff --check without errors. No compile or executed mutex fault tests were performed here. Required later checks remain actual Windows compilation, controlled create/wait/abandoned/ioctl/release paths and handle counts, successful dual-port regression, and independent two-stick/reboot behavior with Fan Control continuously active.
