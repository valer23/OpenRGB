### [P2] Skip configuration writes for a wholly empty physical port

Locations: RGBController_LianLiUniHubSLInfinity.cpp:426, 446 and 468; LianLiUniHubSLInfinityController.cpp:276-300. When both paired zones have zero LEDs, GetPortFanCount returns zero, but every update entry point still calls SendStartAction. Its guard accepts zero and sends E0 10 60 PP 00 00 00. In the supplied 3/2/1/0 topology this writes a configuration to unused port 4; with all zones at their initial zero sizes it can also disable lighting sync and configure all four ports before any populated lighting update. DeviceUpdateMode's empty-channel condition is evaluated after SendStartAction and therefore does not prevent these writes.

The supplied evidence names NN as a fan count and includes an empty port in the topology, so the worker's zero-count interpretation is understandable. However, neither corrected capture nor supplied vendor examples establish that a zero-fan configuration packet is supported, necessary or harmless. This is an unsupported expansion of configuration traffic, not proof of a specific hardware malfunction. The required sparse/empty behavior can be implemented without it: skip a wholly empty paired port before setup, and reject/skip zero-count setup at the low-level boundary before sync/configuration writes. Preserve setup for a populated pair even if one logical zone is empty, and continue to later populated ports. Do not invent a replacement clearing/disable command for a port becoming empty. A separate captured requirement would be needed before implementing that behavior.

Verification gate for the correction: an initially all-empty device sends no lighting reports; 3/2/1/0 sends no setup for port 4; an empty pair preceding a populated pair does not block later updates; a pair with only one populated zone still gets the correct shared positive count; positive-to-empty sends no speculative configuration and later positive count changes remain handled. No code was changed during this review.

The existing device/controller architecture and exact detector remain appropriate. Setup and sync disable use seven-byte feature reports; colour uses a zero-filled 353-byte output report; commit uses a seven-byte feature report with separate speed, direction and brightness bytes. Static sends E0, 10+channel, 01, 00, 00, 00, 00 as clarified in v2. Existing hardware effect IDs, speed/brightness definitions, RBG colour mapping and brightness limiter are retained. Native Sleep provides the supplied Windows 20/5 ms spacing; no cooling commands or timer-resolution/scheduling framework was added.

RGBController_LianLiUniHubSLInfinity.cpp:400-414 uses ceil(max(paired zone lengths)/16) for each physical port. All update paths check setup before dependent channel traffic. Successfully configured positive counts are cached per port and refreshed when changed. Zero-count configuration is the outstanding scope finding above. Empty channels continue rather than exiting the whole mode loop. Partial static groups have zero-filled padding; effect paths send bounded complete fan groups. Static and hardware callbacks retain their correct routing, and single-LED updates now reach the colour path.

The diagnostic feedback is correctly reflected in production logic: CheckReport takes the logical channel; failed/short sync, setup, colour and commit reports set that channel's latch. Both SetChannelLEDs and SetChannelMode return immediately on colour failure, preventing commit. They reset only their own latch after a successful commit following successful colour output (LianLiUniHubSLInfinityController.cpp:144-154 and 247-257). Thus a different channel's success cannot re-arm a persistently failing channel, individual successful colour reports do not flood a failed commit, and a fully recovered channel reports a new failure episode. A setup failure on an empty channel can retain its latch until it later has a successful complete update; this suppresses repetition without affecting later channels.
